# External motion precedent triage

Use this read-only procedure only after the motion entry point has inspected
the existing and system-owned path and established a decision-relevant gap.
The shared restrained-design protocol owns solution ordering and verdict
meaning; this reference adds only motion-specific evidence and ownership rules.

## Establish evidence

Separate what each artifact proves. Visual media can show apparent sequence and
continuity; a live demo can show bounded runtime behavior; source, manifests,
and license can show implementation and stated reuse terms; live Scholium
construction can show the actual target owner. None proves the others.

Open authoritative source rather than relying on snippets or imitation. Mark
source, license, dependency, accessibility, portability, containment,
performance, and interruption claims unverified when evidence is absent.

## Locate the owner

Name the exact task and determine whether native view state, AppKit geometry,
system feedback, or the bounded editor/reader owns it. Motion may present a
change but cannot create a second selection, navigation, buffer, save, focus,
conflict, or recovery fact.

Inspect only decision-relevant applicability: runtime and framework, dependency
and packaging boundary, stable integration owner, lifecycle, exact-source and
research invariants, alternate input and reduced motion, containment, privacy,
and verified reuse terms.

## Verdict

Apply the shared classification and report one verdict per owner when a
transition crosses boundaries. This read-only triage may report reuse, adapt,
translate, or reject; an unresolved minimal-custom or defer decision belongs to
the interface owner. Never issue reuse from a recording or demo alone.

Report the verdict first, then target, evidence inspected, retained intent,
required boundary, dependency and license facts, preserved invariants, later
implementation owner, smallest proof, and uncertainty. Do not emit code during
triage.
