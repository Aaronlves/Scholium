# Scholium component, state, and presentation system

Use this only when a reusable component, presentation contract,
interface-symbol grammar, or motion intent is genuinely in scope. Resolve
current states, components, values, symbols, and framework APIs from live
authority.

Enter only after the interface entry point has established a concrete reusable
responsibility; do not reopen general solution research in this reference.

## Establish responsibility

1. Inventory the live state owner, identity, lifetime, mutation authority,
   consumers, native host, presentation route, cancellation, teardown, and tests.
2. Share only a responsibility whose meaning, lifecycle, adaptation, and proof
   are genuinely common. Similar styling or vocabulary is insufficient.
3. Prefer the native component, then an existing Scholium component, then the
   smallest new semantic surface for the remaining gap.

## Keep layers separate

- Domain, source, workflow, authorization, and operation state remain with
  their existing owner.
- Native controls own their standard interaction state and accessibility.
- A reusable presentation recipe is a pure mapping from typed semantic input
  and ambient policy to visible structure; it performs no I/O or navigation.
- Presentation routes have one owner with typed input, cancellation, completion,
  failure, focus return, and recovery.
- Motion presents an already-defined change; it does not create or mutate state.

Do not create a universal state enum, global presentation model, environment
dump, symbol registry, token family, or motion singleton. Centralize a value
only after product approval and genuine semantic reuse. Keep framework adapters
thin and let each framework retain its geometry, focus, and lifecycle owner.

## Cutover and proof

Apply the typed contract to the complete bounded responsibility and every
matching repository-owned consumer, then delete the superseded owner in the
same change. Broaden it to genuinely distinct consumers only through later
stable product slices. Verify identity, ordinary and consequential states,
input routes, accessibility adaptations, cancellation, focus, recovery, and
reduced-motion meaning as applicable. Update architecture only when real
ownership or dependency direction changes.
